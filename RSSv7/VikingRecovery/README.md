# Восстановление фермы Viking Rise

Общий интерфейс **Viking Tools** объединяет восстановление, повторный вход и создание новых ферм пакетами.
Инструкция: [README_TOOLS.md](README_TOOLS.md). Старые ярлыки Recovery и Login продолжают работать отдельно.

Утилита клонирует чистый LDPlayer ID 0, запускает Viking Rise, автоматически определяет активный профиль по
`SelectedProfile` в `GnBots\config.json`, входит через IGG и переименовывает новый эмулятор в имя фермы.
Поддерживаются как обычные каталоги LDPlayer, так и штатные junction/symlink на отдельный диск.

Если существующий эмулятор исправен, но в нём слетела авторизация, используйте отдельный **VikingLogin**.
Он повторяет только вход в выбранном LDPlayer и ничего не клонирует, не переименовывает и не удаляет. Подробная
инструкция находится в `README_LOGIN.md`.

Если эмулятор с таким именем уже существует, он не удаляется: утилита переименует его в `<ферма>_OLD`.
Если это имя занято, добавится временная метка. Удаление экземпляров утилитой намеренно не реализовано.

## Запуск

Запускайте `run_viking_recovery.bat` непосредственно на рабочем столе Windows-сервера. LDPlayer нельзя
надёжно запускать из фоновой SSH-сессии.

1. Выберите ферму в таблице.
2. Нажмите **Восстановить выбранную ферму**.
3. Подтвердите создание клона и дождитесь сообщения об окончании.

Окно можно оставить открытым. Пароли не отображаются и не записываются в журнал. Утилита использует OCR и
английскую модель Tesseract из установленного GnBots.

После успешного восстановления утилита поднимает своё окно поверх LDPlayer, воспроизводит системный сигнал,
показывает подтверждение с новым ID и оставляет зелёную строку результата. Для загрузки обновлённой версии
после замены файлов закройте уже открытое окно утилиты и запустите ярлык заново.

## Что автоматизируется

1. Проверка чистого образа ID 0, свободного места и согласованности UUID дисков.
2. Повторное использование безопасного незавершённого `RECOVERY_*`-клона либо создание нового.
   Имя нового клона содержит устойчивый ID записи клиента, поэтому одноимённые фермы разных клиентов
   не делят незавершённые клоны. Старые клоны без ID автоматически не подхватываются для записей с ID.
3. Запуск LDPlayer и Viking Rise, ожидание формы авторизации и ввод учётных данных IGG.
4. Выбор игрового ID из поля `Custom`, ожидание загрузки ресурсов и появления игровой карты.
5. Переименование старого экземпляра в `<ферма>_OLD`, а нового — в имя выбранной фермы.
6. Замена `InstanceId` выбранной записи и подтверждённых общих персонажей на ID нового LDPlayer.
   Для общего переноса нужны прежний общий номер, одинаковые IGG-вход и Custom, разные явно включённые
   слоты переключения персонажей. Совпадение одного номера не подтверждает общего владельца.
   У каждой записи сохраняются свои Data/MenuData, Active и номер игрового персонажа.
   Целевой номер не должен принадлежать посторонней записи, включая выключенную. Проверка выполняется
   перед достройкой/запуском клона и повторно перед записью профиля. Старые VM с неподтверждённым владельцем
   не переименовываются. Неоднозначная группа или дублирующийся ID записи блокируют перенос.
   Если профиль менялся параллельно или привязка выбранной фермы устарела, запись блокируется.
   Перед заменой сохраняются обычная и датированная резервные копии профиля.

Если запись была удалена из профиля после отказа от продления, сначала нажмите «Оплачено» в UsersDash.
UsersDash восстановит полную запись строго по её `internal_id` из ежедневного архива и пометит её как
ожидающую новый LDPlayer. После входа в игру и подтверждённого переименования Viking Recovery атомарно
запишет новый ID и включит подготовленную запись. RSSv7 подтвердит возобновление в UsersDash.
Архивный `InstanceId` при этом сбрасывается в `-1`: номер мог уже перейти новому клиенту. Новый клон
получает свободный индекс от LDPlayer, занятый номер не освобождается и чужой профиль не меняется.
В Viking Tools удалённую запись можно также выбрать через **Показать удалённые из архива**:
строка создаётся полностью из последнего дневного архива по постоянному ID, затем новый индекс
сохраняется после успешного входа. Подробности — в `README_TOOLS.md`.

Профиль обновляется атомарно и сразу перечитывается для проверки. Перед заменой рядом с ним сохраняется
резервная копия `<имя профиля>.before_viking_recovery`. Если запись или проверка не удалась, восстановление не
помечается успешным и утилита показывает ошибку.

Если LDPlayer при копировании junction-образа создаст VMDK, но не создаст `.vbox`, утилита восстановит
метаданные только для принадлежащего ей `RECOVERY_*`-клона и повторно проверит UUID перед первым запуском.
Если копирование оставит только `data.vmdk` или урезанный `leidianN.config`, утилита атомарно докопирует
недостающие диски и параметры из ID 0, сохранив созданные для клона IMEI, Android ID, MAC и имя.

Во время стартовой загрузки игра может несколько минут скачивать ресурсы. В этот период автоматизация ничего
не нажимает: переход к `Confirm` и `IGG Account` выполняется только после распознавания соответствующего
экрана. Текст OCR передаётся из Windows PowerShell в Base64, поэтому случайные кавычки в ошибочно распознанном
логотипе не повреждают JSON; единичный сбой OCR считается временным и автоматически проверяется повторно.

## Диагностика

Безопасная проверка окружения без создания клона:

```bat
py -3 viking_recovery.py --check
```

Проверка конкретной записи без изменения LDPlayer:

```bat
py -3 viking_recovery.py --farm Akhm2 --dry-run
```

Для явного выбора удалённой записи в CLI добавьте `--from-archive`; при одинаковых именах укажите
`--record-id ПОСТОЯННЫЙ_ID`. `--list --from-archive` только показывает список, `--dry-run` не создаёт строку.
Перед реальным CLI-восстановлением GnBots и его мониторы должны быть остановлены; Viking Tools управляет
этим автоматически и восстанавливает работу сервера после операции.

Для автоматизированного запуска из интерактивной задачи Windows можно использовать
`run_viking_recovery_cli.cmd ИМЯ_ФЕРМЫ`. Результат пишется в `logs\viking_recovery_cli.log`.

Перед первым запуском проверяется соответствие UUID в `.vbox` и VMDK, чтобы не запускать повреждённый клон с
ошибкой `InvalidMedium`. Журнал находится в `logs\viking_recovery.log` и не содержит Email/Password. При ошибке новый экземпляр не
удаляется автоматически, чтобы не потерять уже загруженные данные и оставить возможность диагностики.
